# Безопасность

> Статус: реализованы auth-service (шаг 3), API Gateway (шаг 4) и общая проверка токенов во всех сервисах (шаг 2). Проверки владения ресурсами в бизнес-сервисах дополняются на шагах 5–9.

## Роли

| Роль | Как получить | Возможности (итоговые) |
|---|---|---|
| `CLIENT` | Автоматически при публичной регистрации | Абонементы, оплата, записи, свои уведомления |
| `TRAINER` | Назначает ADMIN (`PATCH /api/admin/users/{id}/roles`) | Свои занятия и списки участников. Может одновременно оставаться CLIENT |
| `ADMIN` | Первый — bootstrap из конфигурации, остальных назначает ADMIN | Тарифы, расписание, роли |

- В DTO регистрации **нет поля ролей**. Если клиент пришлёт `"roles":["ADMIN"]`, поле будет проигнорировано, а назначится только `CLIENT` (тест `publicRegistrationAssignsOnlyClientAndIgnoresRequestedRoles`).
- Право назначать роли проверяется дважды: `@PreAuthorize("hasRole('ADMIN')")` на контроллере и повторно в `ChangeUserRolesUseCase`.
- ADMIN не может снять роль ADMIN с самого себя (`CANNOT_REVOKE_OWN_ADMIN`): так клуб не останется без администратора.

## Учётные записи и пароли

- **Email.** Нормализуется (`strip` + нижний регистр) в value object `Email`. Уникальность обеспечивает ограничение БД `uq_users_email`, а `CHECK` не даёт сохранить ненормализованное значение. Параллельная регистрация одного email даёт ровно одного пользователя (тест `concurrentRegistrationWithSameEmailCreatesExactlyOneUser`).
- **Пароль.** Хешируется стандартным `BCryptPasswordEncoder`. Правила `PasswordPolicy`: не меньше 8 символов и **не больше 72 байт в UTF-8**. BCrypt учитывает только первые 72 байта, а кириллица занимает 2 байта на символ: 36 символов допустимы, 37 — нет.
- **Вход.** Неизвестный email, неверный пароль и отключённая учётная запись дают одинаковый ответ `401 INVALID_CREDENTIALS`. Для неизвестного email пароль всё равно сверяется с фиктивным хешем, чтобы время ответа не выдавало, существует ли пользователь.

## Пользовательские JWT (access)

| Параметр | Значение |
|---|---|
| Алгоритм | **RS256**. Закрытый ключ есть только у auth-service (`jwt_private_key.pem`), публичный — у всех сервисов |
| Срок | 15 минут (`fitclub.auth.access-token-ttl`) |
| Claims | `iss=fitclub-auth`, `aud=fitclub-api`, `sub`=UUID пользователя, `iat`, `exp`, `jti`, `roles`, `name` |
| Проверка | Локально в каждом сервисе (`JwtDecoders.rs256`): подпись, только RS256 (HS256 и `none` отклоняются), `iss`, `aud`, наличие и срок `exp`, `nbf`, наличие `sub`. HTTP-запроса в Auth на каждый запрос нет |
| Роли → права | Claim `roles` превращается в `ROLE_CLIENT` / `ROLE_TRAINER` / `ROLE_ADMIN`. Неизвестные значения отбрасываются |
| Ключи | Генерирует `GenerateSecrets.java` и не перезаписывает при повторном запуске. При старте auth-service проверяет, что закрытый ключ соответствует публичному |

`user_id` в пользовательских операциях всегда берётся из проверенного `sub` (параметр `AuthenticatedUser` в контроллерах), а не из тела запроса.

## Refresh-токены

- 256 случайных бит (`SecureRandom`). Клиент получает токен один раз, в БД хранится **только SHA-256** (`refresh_tokens.token_hash`).
- Срок — 7 дней (`fitclub.auth.refresh-token-ttl`), интервал `[issued_at, expires_at)`.
- **Ротация.** Каждый `POST /api/auth/refresh` помечает старый токен заменённым (`replaced_by`) и выдаёт новый в той же цепочке (`family_id`). Строка блокируется `SELECT … FOR UPDATE`, поэтому две параллельные ротации одного токена невозможны.
- **Повторное использование.** Если предъявлен уже заменённый токен (признак кражи), отзывается вся цепочка, включая последний выданный токен.
- **Logout.** `POST /api/auth/logout` с refresh-токеном отзывает цепочку и идемпотентен.

**Ограничение.** Уже выданный access JWT **остаётся действительным до своего `exp`** (не более 15 минут) даже после logout или смены ролей. Сервисы проверяют его локально и не обращаются к Auth. Немедленного отзыва access-токенов в проекте нет. Новые роли попадают в токен при следующем входе или refresh.

## Токены в браузере

UI (шаг 10) будет хранить access и refresh **только в памяти вкладки**: не в `localStorage`, не в cookie, не в URL. После перезагрузки страницы нужен повторный вход. Ответы с токенами отправляются с `Cache-Control: no-store`. Токены, пароли и заголовок `Authorization` не логируются: проверено по логам контейнера.

## CORS и CSRF

- API использует только `Authorization: Bearer`. Cookie-сессий нет (`SessionCreationPolicy.STATELESS`, form login и HTTP Basic отключены).
- **CSRF отключён**. Атака CSRF возможна, когда браузер сам прикладывает учётные данные (cookie). Bearer-токен из памяти JavaScript браузер автоматически не отправляет.
- **CORS не настраивается.** UI и API работают с одного origin: Nginx проксирует `/api` в Gateway. Ответы без CORS-заголовков, поэтому чужие сайты не могут читать API из браузера.

## Межсервисные вызовы (`/internal/**`)

| Направление | Секрет | Разрешённые пути |
|---|---|---|
| schedule-service → auth-service | `service_token_schedule_to_auth` | `/internal/users/**` |
| payment-service → membership-service | `service_token_payment_to_membership` | `/internal/membership-orders/**` |
| booking-service → membership-service | `service_token_booking_to_membership` | `/internal/memberships/**` |

- Токен передаётся в `X-Service-Token`, сравнивается за постоянное время (`MessageDigest.isEqual`) и действует только на путях своего направления: токен booking на маршруте payment получит 403. Неверный или отсутствующий токен — 401.
- Пользовательский JWT внутренние маршруты не открывает.
- Секреты разные для каждого направления, лежат в `secrets/` и монтируются только в нужные контейнеры.
- Gateway не публикует `/internal/**` (ответ `404`) и удаляет `X-Service-Token` из входящих запросов. Внутренний endpoint при этом проверяет токен сам: Gateway — не единственная линия защиты.
- **Учебное решение для закрытой сети контейнеров.** Развитие — короткоживущие service JWT от отдельного издателя или mTLS между сервисами. В текущий объём это не входит.

## API Gateway

- Проверяет пользовательский JWT по тем же правилам, что и сервисы (RS256, `iss`, `aud`, `exp`, `sub`). Без токена или с недействительным токеном запрос до сервиса не доходит (`401` problem+json).
- **Роли и владение не проверяет.** Это делает сервис: даже если обойти Gateway (например, через dev-порт 8081–8086), сервис сам отклонит запрос.
- Пути с `..`, `//`, `;`, `\` и их кодированными формами отклоняются до маршрутизации: иначе `/api/../internal/x` совпал бы с `/api/**`, а сервис нормализовал бы его в `/internal/x`.
- `X-Forwarded-*` передаются сервисам только для запросов из loopback и частных сетей (`trusted-proxies`). Сервисы используют их лишь для построения URL в OpenAPI.
- Сессий, cookie и CSRF нет, CORS не настраивается.

## Тестовая оплата

- `POST /api/payments/{id}/simulate` создаётся только при `fitclub.payment.simulation-endpoint=true`. Свойство включают профили `local`, `demo` и `test`. В рабочем профиле `docker` маршрута нет.
- Завершить можно только **свой** платёж: владелец берётся из JWT. Чужой платёж отвечает 404.
- Сумма платежа не принимается от клиента: она берётся из снимка заказа через внутренний API Membership. Membership при активации ещё раз сверяет сумму, валюту и владельца.
- Симулятор не запрашивает и не хранит данные карты. Это намеренный demo-механизм, а не интеграция с банком.

## Секреты

- Каталог `secrets/` и `.env` исключены из Git. В `.env.example` только порты и email администратора.
- `GenerateSecrets.java` создаёт недостающие секреты, существующие не перезаписывает и значения не печатает.
- В контейнер секреты попадают через Compose secrets (`/run/secrets`). Закрытый ключ JWT и пароль первого администратора монтируются только в auth-service.

## Первый администратор

`EnsureInitialAdminUseCase` выполняется при запуске auth-service, если заданы email (`FITCLUB_AUTH_INITIAL_ADMIN_EMAIL`, по умолчанию `admin@fitclub.local`) и пароль (секрет `auth_initial_admin_password`). Если ADMIN уже есть, ничего не меняется. Без секрета с паролем администратор не создаётся. Это явное bootstrap-действие, а не demo-данные. Demo-пользователей создаёт отдельный demo-профиль (шаг 10).
